Return-It · System design

Ingestion Architecture

Four different ways a return can arrive. One parser. The sequencing isn't an engineering preference — it's the shape Google's restricted-scope rules force, turned into an advantage.

26 August 2026 Pilot v1 — 20–100 users Status: design agreed, unimplemented

The load-bearing rule

Only Layer 1 changes when Gmail is added. Layers 2 and 3 never learn where the bytes came from.

Three layers, hard boundaries

The boundaries are the design. Each layer can be understood, tested and replaced without opening the other two.

Layer 1

Ingestion adapters

Each turns some inbound thing into a RawReturnDocument. Small, dumb, and completely ignorant of parsing.

  • ForwardAdapter — unique per-user inbound address
  • UploadAdapter — file or pasted email body
  • OutlookAdapter — Microsoft Graph
  • GmailAdapter — Gmail History API

Layer 2

Parser core

RawReturnDocument → DetectedReturn. Pure functions, no I/O, fully testable against a fixture corpus of real UK return emails.

  • Retailer identification by sender domain and template signature
  • Deadline extraction
  • Carrier and return ID
  • Label detection — PDF attachment, QR, or link
  • Confidence score gating auto-accept vs. “confirm this?”

Layer 3

Domain + UI

Where a DetectedReturn becomes something a person acts on. Builds on the quote and booking flow that already exists.

  • Pending Returns dashboard
  • Pickup scheduling
  • Existing quote & booking flow

The contract every adapter narrows to

type RawReturnDocument = {
  userId:       string
  source:       'forward' | 'upload' | 'outlook' | 'gmail'
  receivedAt:   Date
  senderDomain: string
  subject:      string
  body:         string
  attachments:  Attachment[]
}

source is recorded for provenance and debugging — the parser never branches on it.

Why the sequencing is what it is

The order isn't taste. Each path carries a different authorisation regime, and one of them quietly breaks the product it's meant to enable.

Path Authorisation Gate to production Ceiling Cost
Forwarding address None — the user forwards No gate None £0
Outlook · Graph Mail.Read delegated Publisher verification None £0
Gmail · gmail.readonly Restricted scope CASA Tier 2 third-party DAST by an authorised lab, annual recert 100 manually-allowlisted testers until verified ~$500–$4,500 / yr

The fact that decides the order

While a Google app sits in Testing status, refresh tokens expire after seven days. Every pilot user would have to re-authorise weekly — in a product whose entire promise is “it watches so you don’t have to.” Gmail-first isn’t expensive so much as self-defeating.

Microsoft Graph has no CASA equivalent, no user cap, and no seven-day expiry. So Outlook ships first and becomes the live, demoable “connected inbox” proof point months before Gmail clears verification.

The phasing

A real sequence — each phase unlocks the evidence the next one needs.

01

V1 · now

Forward + upload

Both doors open at once, feeding one parser and one dashboard. No OAuth, no caps, no expiry — and the honest consent story: we only ever see what you forward us.

02

V1.5

Outlook connect

One new adapter. The first true connected-inbox experience, live and demonstrable while Gmail verification is still in flight.

03

V2

Gmail connect

Applied for with evidence in hand: N retailers parsed at X% accuracy across M pilot users. One more adapter, nothing downstream touched.

Why this ordering is also the strategy

Ingestion is commodity. The parser is the asset.

Anyone can call the Gmail API. What’s hard is reliably pulling a deadline and a carrier out of forty different UK retailer email templates. Building parser-first means a labelled corpus of real return emails accumulates from day one — the defensible artifact, and the thing that makes the eventual restricted-scope application credible.

You apply with “we already process this reliably, at this accuracy, for these users” rather than “we’d like to read inboxes, please.”
